# CLAUDE.md — Development Rules for Contro

> **Status:** APPROVED by owner 2026-10-17

Read `PROJECT.md` (scope), `ARCHITECTURE.md` (decisions), and `ROADMAP.md` (current task) before starting work.

## Roles

- **Owner (GitHub `soncsec`):** approves scope, architecture, merges, and production deployments.
- **Claude:** implements approved tasks, writes tests, runs checks, prepares PRs, and keeps the docs current.

## Scope boundary (other Claude sessions build other games)

- Change files only inside this repo. Never edit Star Destroyer, the portal repo, or shared assets.
- Reading the other repos for reference is fine (`~/dev/games/stardestroyer`, `~/dev/games/games-portal`).
- `legacy/` (the art pack) is read-only. It links to the shared `~/dev/games/_assets/legacy/`. Copy what you need into `public/assets/`.
- Changes another repo needs (for example, Contro's portal card) go through a PR or issue on that repo, worked in a separate clone, never in that repo's local folder.
- On the production server, this game may only write to `/var/www/html/soncrant.com/pub/games/contro` and `/srv/games-releases/contro/`.
- Local ports: dev **5174**, preview **4175**, Playwright **4176**.

## Always ask the owner before

- Changing the architecture or any ADR, or adding a dependency not listed in ARCHITECTURE.md
- Changing scope (adding or dropping features)
- Destructive operations: deleting files or branches, force-pushing, rewriting history, deleting repos
- Any change on the production server other than releasing this game, or any change to its Apache configuration
  - **Standing approval (owner, 2026-10-17):** Claude may release each playable increment of Contro with `scripts/release.sh deploy`, without asking each time. The script still requires every CI check (including CodeQL and the ZAP staging scan) to have passed on `main`, and rolls back automatically if the smoke test fails. Report every release (id, what changed, smoke test and scan results).
- Security decisions: CSP and header policy, SSH keys, secrets handling, permissions, CI tokens
- Adding new third-party assets (art, audio, fonts), including anything outside `legacy/`

## Git workflow

- Never commit or push directly to `main`, and never merge PRs. The owner merges.
- One task per branch, named `feature/<roadmap-id>-<short-name>` (e.g. `feature/M1.4-player-movement`).
- Small PRs, one roadmap task each. The PR description includes:
  - a summary of the change (what and why)
  - test evidence: commands run and results, plus screenshots for visual changes and map edits
  - the roadmap task ID and its acceptance criteria, each marked met or not met
- Commit messages are short and in the imperative mood.
- Never commit `legacy/`, `node_modules/`, `dist/`, secrets, or `.env` files.

## Quality rules

- A task is **not done** until its acceptance criteria are verified against the running game, not just because code exists.
- Never weaken, skip, or delete a test to make it pass. If a test seems wrong, explain why in the PR and ask.
- Every PR must pass: `npm run format:check`, `npm run lint`, `npm run typecheck`, `npm test`, `npm run test:e2e`, `npm run build`, `npm audit --audit-level=high`.
- Game rules go in `src/logic/` as plain TypeScript (no Phaser imports) with unit tests; 80% coverage minimum.
- Gameplay numbers go in `src/config/tuning.ts`. No magic numbers in scenes.
- Enemies, bosses, weapons and dialogue are data in `src/data/`; levels are Tiled maps validated by tests.
- Use the seeded RNG for anything random in gameplay. Reuse pooled objects.

## Security rules

- No runtime requests to third-party hosts. Everything is bundled and served from our own origin.
- Must run under the portal's CSP: no inline scripts or styles, no `eval`, no `innerHTML`.
- Pin exact dependency versions, at least two weeks old, and commit the lockfile.
- Run static checks (CodeQL, ESLint, `npm audit`, Gitleaks) and a dynamic check (OWASP ZAP baseline) before any deployment or configuration change, and report the results.
- No personal data. localStorage holds only progress, best score and settings.
- Never put credentials or the server's address in code, the chat, or CI logs. Server details stay in the untracked `deploy/server.env`.

## Environment

- Node.js comes from nvm. Run `export NVM_DIR=$HOME/.nvm; . $NVM_DIR/nvm.sh` before using `node` or `npm` in a fresh shell.
- The GitHub CLI is at `~/.local/bin/gh`.
